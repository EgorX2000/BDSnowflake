# Отчет по лабораторной работе №1: Нормализация данных "Снежинку"

## Введение
Целью данной работы была трансформация «плоских» исходных данных из 10 CSV-файлов (суммарно 10 000 строк) в аналитическую модель данных «Снежинка» на базе СУБД PostgreSQL. Работа включала в себя проектирование архитектуры, очистку данных от «шума» и реализацию автоматизированного ETL-процесса через Docker.

---

## Что было сделано:

### 1. Загрузка сырых данных
На первом этапе я создал буферную таблицу `raw_data`, повторяющую структуру CSV-файла. С помощью команды `copy` в базу были импортированы все 10 файлов. Это позволило в дальнейшем работать с данными средствами SQL, не обращаясь к файловой системе напрямую.

### 2. Проектирование архитектуры «Снежинка»
Я разделил исходную таблицу на 6 измерений (Dimensions) и 1 таблицу фактов (Facts):
*   **dim_geography**: Единый справочник стран, городов и почтовых индексов.
*   **dim_categories**: Категории товаров.
*   **dim_suppliers**: Информация о поставщиках (ссылается на географию).
*   **dim_products**: Данные о товарах (ссылается на категории и поставщиков).
*   **dim_customers**: Данные о покупателях (ссылается на географию).
*   **dim_stores**: Данные о магазинах (ссылается на географию).
*   **fact_sales**: Центр модели, содержащий ключи и количественные показатели продаж.

Таблицу географии я использовал в качестве общего измерения для покупателей, магазинов и поставщиков. Это позволило избежать дублирования названий стран/городов и обеспечило высокую целостность данных.

### 3. Очистка данных
В процессе трансформации я осознанно отказался от части исходных данных, чтобы сделать модель более эффективной:
*   **Удаление динамических данных:** Рейтинги и отзывы были исключены, так как они динамически меняются и не подходят для стабильных справочников.
*   **Снижение детализации:** Я убрал информацию о конкретных продавцах (`sellers`), так как для глобального анализа продаж приоритетнее уровень магазинов (`stores`).
*   **Фильтрация шума:** Длинные текстовые описания товаров были отсечены, так как они не несут аналитической ценности для агрегатных отчетов, но сильно увеличивают объем БД.

### 4. Реализация ETL-процесса и решение проблем
В ходе заполнения таблиц я столкнулся с двумя критическими проблемами:
1.  **Декартово произведение:** Из-за неточных JOIN-ов по неуникальным именам товаров объем базы начал расти до гигабайт. Проблема была решена внедрением `distinct on` по составным ключам (например, `название товара + бренд`).
2.  **Проблема NULL-значений:** При связывании таблиц по почтовым индексам потерялась часть данных, так как в SQL `NULL != NULL`. Я исправил это, использовав `is not distinct from`, что позволило сохранить 100% строк.

### 5. Автоматизация через Docker
Для удобства проверки я настроил автоматическую инициализацию базы. При запуске `docker compose up -d`:
1.  Создается структура таблиц.
2.  Данные из папки `исходные данные` копируются в `raw_data`.
3.  Выполняются скрипты трансформации и распределения данных по «снежинке».

## Результаты
Для проверки корректности были написаны скрипты верификации:
*   **Целостность:** Количество строк в таблице фактов (`fact_sales`) совпадает с исходными данными — ровно **10 000** записей.
*   **Финансы:** Итоговая сумма выручки в нормализованной модели полностью совпадает с исходным логом.
*   **Связи:** Тестовые JOIN-запросы успешно собирают данные из самых удаленных узлов снежинки (например, выводят продажи в разрезе стран поставщиков).

## Вывод
В результате работы была создана нормализованная модель данных, избавленная от избыточности и готовая для построения сложных аналитических отчетов. Архитектура «Снежинка» с общей географией обеспечила оптимальный баланс между экономией места и удобством анализа.
